# Архитектура потоковой обработки данных: Go API → Kafka → ClickHouse

В этом документе описаны ключевые теоретические концепции, архитектурные решения и паттерны взаимодействия сервиса трекинга событий (`track_api_go`), брокера сообщений (Apache Kafka) и аналитической базы данных (ClickHouse).

---

## 1. Общая архитектурная схема

```text
  [Клиенты / Пользователи]
             │
             ▼ (HTTP / gRPC запросы)
   ┌─────────────────────────────────────────┐
   │         Go API (Сервис трекинга)        │
   │                                         │
   │  [Хэндлеры бизнес-логики]               │
   │             │                           │
   │             ▼                           │
   │  [Kafka Producer (библиотека franz-go)] │
   └─────────────────────────────────────────┘
             │
             │ Батчинг №1 (Ограничение по размеру ИЛИ Linger: ~5ms)
             ▼
   ┌─────────────────────────────────────────┐
   │             Apache Kafka                │
   │        (Брокер / Очередь событий)       │
   └─────────────────────────────────────────┘
             │
             │ Батчинг №2 (Размер пачки ИЛИ Таймаут: ~1–2s)
             ▼
   ┌─────────────────────────────────────────┐
   │              ClickHouse                 │
   │       (Колоночная аналитическая БД)     │
   └─────────────────────────────────────────┘
             │
             ▼
    [Аналитики / BI / Grafana]
```

---

## 2. Роли компонентов системы

1. **Go API (`track_api_go`) — Роль: Producer (Продюсер):**
   - Принимает сырые события от внешних клиентов с минимальной задержкой.
   - Валидирует и нормализует данные.
   - Внутри себя инициализирует клиент Kafka (`kgo.Client`), который буферизует сообщения и отправляет их в брокер.
2. **Apache Kafka — Роль: Message Broker / Distributed Log:**
   - Выступает буфером отказоустойчивости (shock-absorber).
   - Сглаживает пиковые нагрузки: даже если ClickHouse временно недоступен или замедлился, Kafka сохраняет все события на диске.
   - Гарантирует упорядоченность событий внутри партиций.
3. **ClickHouse — Роль: Consumer / Analytical Storage:**
   - Колоночная СУБД, оптимизированная для сверхбыстрых аналитических агрегаций (`COUNT`, `SUM`, воронки, retention).
   - Не предназначена для построчной вставки (OLTP); требует вставки крупными пакетами.

## 3. Двухуровневый батчинг (Batching)

Батчинг — это механизм накопления мелких записей в один пакет перед физической отправкой или записью.

### Золотое правило отправки батча:
Отправка пакета происходит по логическому условию **ИЛИ (`OR`)**:
> **Пакет отправляется, ЕСЛИ:**
> 1. `Текущий_размер_буфера >= Лимит_размера`  
>    **ИЛИ**
> 2. `Прошедшее_время >= Лимит_таймаута`

Это правило решает две ключевые проблемы:
- **При высокой нагрузке (Peak Load):** буфер заполняется мгновенно, пачки улетают по лимиту размера без искусственных пауз.
- **При низкой нагрузке (Idle/Night):** таймер сбрасывает даже одно накопившееся сообщение, не заставляя систему ждать заполнения буфера часами.

---

### Уровни батчинга в нашей системе:

| Параметр | Уровень 1: Go API → Kafka | Уровень 2: Kafka → ClickHouse |
| :--- | :--- | :--- |
| **Где происходит** | В оперативной памяти Go API (библиотека `franz-go`) | В консьюмере / `Kafka Engine` в ClickHouse |
| **Какую проблему решает** | Экономия CPU и сетевых пакетов (syscalls, TCP overhead, сжатие) | Защита ClickHouse от ошибки `Too many parts` |
| **Условие по времени** | `ProducerLinger` (~5 мс) | `stream_flush_interval_ms` (~1–2 секунды) |
| **Условие по размеру** | `ProducerBatchMaxBytes` (~64–256 КБ) | `kafka_max_block_size` (~10 000 – 65 536 строк) |
| **Итоговая задержка** | Менее 10 мс | Около 1–2 секунд (Near Real-Time) |

---

## 4. Почему ClickHouse требует батчинга?

Архитектура хранения ClickHouse основана на структуре **LSM-Tree / MergeTree**:
1. На каждый выполненный запрос `INSERT` ClickHouse создаёт на диске отдельную неизменяемую директорию (кусок данных — **Part**).
2. Фоновые процессы ClickHouse постоянно объединяют (merge) мелкие куски в более крупные.
3. Если отправлять по 10 000 отдельных `INSERT` в секунду, количество несохранённых частей на диске лавинообразно растёт, фоновые мерджи не успевают, и база аварийно отклоняет запросы с ошибкой:
   > `DB::Exception: Too many parts in all data in table... Merges are processing significantly slower than inserts.`
4. Вставка пачками по 5 000–50 000 строк создаёт один компактный кусок сразу со сжатием LZ4/ZSTD, позволяя ClickHouse переваривать миллионы записей в секунду без нагрузки на диск.

## 5. Паттерны в коде Go (`franz-go`)

### 5.1. Синхронная (`Publish`) vs Асинхронная (`PublishAsync`) отправка
- **`Publish` (`ProduceSync`):** Текущая горутина блокируется и ждёт подтверждения (ACK) от брокера. Применяется для финансовых транзакций, где критично немедленно вернуть клиенту результат операции.
- **`PublishAsync` (`Produce` + Callback):** Сообщение кладётся в локальную очередь продюсера в памяти, горутина мгновенно продолжает работу. Отправка и батчинг происходят в фоновых горутинах библиотеки. Применяется для метрик, логов, трекинга кликов и аналитики.

### 5.2. Структурный адаптер (`Client struct`)
В Go запрещено объявлять методы на типах из сторонних пакетов:
```go
// Ошибка компиляции:
func (c *kgo.Client) Publish(...) error {}
```
Поэтому создаётся внутренняя структура-адаптер:
```go
type Client struct {
    client *kgo.Client
}
```
Это даёт:
1. Возможность реализовать собственный интерфейс `Producer` для удобного мокирования в юнит-тестах.
2. Сокрытие низкоуровневых параметров `franz-go` от слоя бизнес-логики сервиса.
3. Защиту от Vendor Lock-in (при смене брокера или библиотеки слой логики остаётся неизменным).
