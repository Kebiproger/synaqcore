# Архитектура потока данных: Kafka vs RabbitMQ и асинхронный пайплайн

В этом документе описаны фундаментальные принципы работы брокеров сообщений, асинхронной публикации и почему в проекте выбран стек Kafka (Redpanda) + ClickHouse.

---

## 1. Как работает асинхронная публикация в Kafka

Когда сервис `track_api_go` публикует событие, оно проходит через трёхзвенный конвейер:

```
[HTTP Handler (HandleTrack)]
       │
       ▼ (1) Запись в память за ~1 мкс
[Кольцевой буфер franz-go в RAM] ────► HTTP-клиент сразу получает ответ 200 OK!
       │
       ▼ (2) Фоновый сборщик (Linger 5ms) объединяет сотни событий в сжатый батч (Zstd)
[Батч сообщений: 500 штук]
       │
       ▼ (3) Один TCP-запрос
[Брокер Kafka / Redpanda] ───► Запись в конец файла (Append-only log)
       │
       ▼ (4) Подтверждение (ACK)
[Вызов callback onDone(r *kgo.Record, err error)]
```

### Зачем в `onDone` передаётся структура `*kgo.Record`?
Сигнатура функции обратного вызова:
```go
func(r *kgo.Record, err error)
```
При отправке тысяч событий в секунду, если произойдёт сетевой сбой, переменная `err` скажет только о характере проблемы (например, `timeout`). 
Параметр `r *kgo.Record` содержит контекст:
* `r.Key`: ключ партиционирования (`user_id`);
* `r.Value`: исходный JSON (`payload`), который можно спасти или переотправить;
* `r.Topic`, `r.Partition`, `r.Offset`: точные метаданные в брокере.

## 2. Kafka против RabbitMQ: Ключевые различия

Хотя обе системы передают сообщения, они построены на противоположных концепциях:

| Критерий | RabbitMQ | Apache Kafka / Redpanda |
| :--- | :--- | :--- |
| **Архитектурная модель** | **Очередь сообщений (Smart broker, dumb consumer)** | **Распределённый журнал (Dumb broker, smart consumer)** |
| **Судьба сообщения** | **Удаляется сразу** после подтверждения прочтения (ACK). | **Хранится на диске** заданное время (дни/месяцы) независимо от чтения. |
| **Повторное чтение (Replay)** | **Невозможно.** Прочитанное сообщение исчезает. | **Возможно в любой момент.** Консьюмер может сдвинуть `offset` назад. |
| **Модель получения** | **Push:** Брокер сам проталкивает сообщения клиентам. | **Pull:** Консьюмеры запрашивают батчи по мере готовности. |
| **Маршрутизация** | Сложная и гибкая (Exchanges: Topic, Fanout, Direct, Headers). | Простая: Сообщения пишутся строго в Топик и Партицию по ключу. |
| **Пропускная способность** | Десятки тысяч сообщений/сек. | **Миллионы сообщений/сек** за счёт батчинга, сжатия и секвентального I/O. |
| **Идеально для** | Задач воркеров: отправка email, генерация PDF, фоновые фоновые джобы. | Потоковой аналитики, логов, трекинга кликов, интеграции с ClickHouse. |

## 3. Схема интеграции ClickHouse + Kafka

ClickHouse забирает данные из топика автоматически силами трёх компонентов:

1. **`ENGINE = Kafka` (Буфер чтения):** Виртуальная таблица, фоново вычитывающая сообщения топика. На диске ничего не сохраняет.
2. **`MATERIALIZED VIEW` (Триггер на INSERT):** Потоковый трансформер. При получении микробатча запускает `SELECT` и направляет данные в постоянную таблицу.
3. **`ENGINE = MergeTree` (Постоянное хранилище):** Колонки сжимаются и раскладываются по партициям (`PARTITION BY toYYYYMM(timestamp)`).
