# Профиль `scale`: ClickHouse и Kafka-пайплайн

> **ClickHouse больше не входит в стек по умолчанию.** События по умолчанию пишутся в `postgres-app`
> (схема `events`), см. [ADR 0003](../adr/0003-postgres-default-event-store.md). ClickHouse — необязательный профиль
> compose `scale`: `make up-scale` (`EVENT_STORE=clickhouse`, нужен `CLICKHOUSE_PASSWORD`, суммарно ≈ 3.2 ГБ
> `mem_limit`, то есть VPS от 4 ГБ). Он даёт полный отчёт `/stats` (сегменты, воронка, выбросы). Данные из Postgres в
> ClickHouse и обратно не переносятся.

Документ описывает, как события попадают в ClickHouse в этом профиле (прямая запись из Go-сервиса `synaq`) и как
устроен паттерн **Kafka Engine → Materialized View → MergeTree**, который вернётся позже (фаза 3 профиля `scale`;
он же работал в Python-версии, тег `v1-python`). Разделы 3–5 (MergeTree, `Nullable`, дедупликация) относятся к
ClickHouse в обоих режимах.

## 0. Прямая запись из synaq (`EVENT_STORE=clickhouse`)

```
[ Браузеры / бэкенды / SDK ]
         │  POST /api/v1/tracker/events (через gateway, limit 200 r/s с IP)
         ▼
[ synaq: валидация → ограниченный буфер в памяти ]
         │  батч: CH_BATCH_SIZE = 1000 событий или раз в CH_FLUSH_INTERVAL = 1 с
         ▼  INSERT INTO tracking_events FORMAT JSONEachRow (async_insert=1, wait_for_async_insert=1)
[ tracking_events (ENGINE = ReplacingMergeTree(timestamp)) ]
         │
         ▼
[ analytics_api: /api/v1/stats/ ]
```

- Включается `EVENT_SINK=clickhouse` у synaq и `EVENTS_BACKEND=clickhouse` у `analytics_api` (compose выставляет оба из
  `EVENT_STORE`). Реализация — `apps/synaq/internal/sink/clickhouse` на общей механике буфера
  `apps/synaq/internal/sink/batch`; схема — только
  [`infra/clickhouse/init/01-tables.sql`](../../infra/clickhouse/init/01-tables.sql). Kafka-очереди и MV нет.
- Буфер ограничен и числом событий (`CH_BUFFER_SIZE`, по умолчанию 10 000), и байтами (`CH_MAX_BUFFERED_BYTES`,
  64 МиБ). В Postgres-режиме те же роли у `EVENTS_*` (батч 500, буфер 32 МиБ). Если он полон, трекер сразу отвечает `503` + `Retry-After: 1`, запрос не блокируется.
- Сетевые ошибки, `5xx` и `429` от ClickHouse повторяются: до 5 попыток с паузами 0.2 → 0.4 → 0.8 → 1.6 с
  (верхняя граница паузы 3 с не достигается); худший случай — ~3 с на батч при отклонённом соединении и до ~53 с,
  если ClickHouse завис (5 × `HTTPTimeout` 10 с + паузы). Батч, который
  так и не записался (или получил `4xx` — ошибку данных), отбрасывается с записью в лог. При штатной остановке
  synaq дописывает буфер (до 5 с).
- **Компромисс:** долговременного буфера нет. Клиент получает `200`, когда событие принято в буфер, а не когда оно
  записано. Если ClickHouse недоступен дольше нескольких секунд, батчи, исчерпавшие попытки, теряются, буфер
  заполняется, и новые события получают `503` (их можно повторить с тем же `event_id`). При падении процесса
  содержимое буфера теряется. Для A/B-аналитики это допустимо, для биллинга — нет. Профиль `scale` (и дисковый
  spool в планах) закрывает этот разрыв.
- Имя таблицы в `INSERT` зашито в код, а не берётся из конфигурации (исключает подстановку SQL).
- Отличия от Postgres-режима: дедупликация только при фоновых слияниях и остаётся **последняя** строка (в Postgres —
  сразу при вставке, **первая**); нет `synchronous_commit=off`-окна, но и буфер synaq так же теряется при падении
  процесса; нет автоматического хранения по сроку (retention) — партиции помесячные и не удаляются.
- Событий, записанных до перехода на Postgres, в Postgres нет: они остаются в томе ClickHouse и видны только в этом
  профиле.

## Фаза 3 профиля `scale` (планируется): Kafka Engine + Materialized View

Ниже — как устроен пайплайн через брокер. Сейчас его нет (ни в стеке по умолчанию, ни в профиле `scale`); DDL очереди и MV (`02-kafka.sql`) лежит в теге
`v1-python` и вернётся вместе с профилем `scale`.

## 1. Общая схема и поток данных

В ClickHouse интеграция с Kafka построена на паттерне из **трёх компонентов**:

```
[ Продюсеры / Бэкенд ]
         │
         ▼
[ Kafka / Redpanda Topic: tracking_events ]
         │
         ▼ (фоновое чтение батчами)
[ 1. Таблица-буфер (ENGINE = Kafka) ]
   tracking_events_queue
         │
         ▼ (триггер вставки на каждый батч)
[ 2. Материализованное представление ]
   tracking_events_mv (AS SELECT ...)
         │
         ▼ (INSERT INTO)
[ 3. Физическая целевая таблица ]
   tracking_events (ENGINE = MergeTree)
         │
         ▼
[ Аналитические запросы / Дашборды / BI ]
```

ClickHouse не сохраняет сообщения напрямую в таблицу с движком Kafka. Для надёжного и быстрого сохранения используется связка **Очередь -> Триггер (MV) -> Физическая таблица**.

---

## 2. Роль каждого компонента

### Компонент 1: Входная очередь (`ENGINE = Kafka`)
* **Роль:** Временный сетевой буфер и консьюмер.
* **Физическое хранение:** **Отсутствует.** Таблица не хранит строки на диске. Это виртуальный интерфейс к Kafka.
* **Поведение:**
  - Напрямую делать `SELECT` из этой таблицы в продакшене **нельзя**: при каждом таком запросе ClickHouse вычитает очередную порцию сообщений и сдвинет смещение (offset), из-за чего данные будут утеряны для постоянного хранилища.
  - Сама по себе таблица Kafka пассивна. Чтобы она начала вычитывать сообщения в фоне, к ней обязательно должно быть привязано хотя бы одно `Materialized View`.

В Python-версии эта таблица описывалась в `infra/clickhouse/init/02-kafka.sql` (тег `v1-python`; файл нужен только
в режиме с Kafka, таблица `tracking_events` — в `01-tables.sql`, который выполняется раньше по алфавиту):

```sql
CREATE TABLE IF NOT EXISTS tracking_events_queue (
    timestamp DateTime64(3, 'UTC'),
    user_id String,
    event_id String,
    event_name String,
    experiment_name String,
    variant String,
    event_data String
) ENGINE = Kafka
SETTINGS kafka_broker_list = 'redpanda:9092',
         kafka_topic_list = 'tracking_events',
         kafka_group_name = 'clickhouse_tracking_cg',
         kafka_format = 'JSONEachRow',
         kafka_handle_error_mode = 'stream',
         input_format_null_as_default = 1;
```

> **У колонок Kafka-таблицы не должно быть `DEFAULT`.** ClickHouse 24.8 отклоняет такой `CREATE` (`BAD_ARGUMENTS`),
> и на свежем томе очередь и MV просто не создавались, хотя трекер успешно писал в Redpanda. Отсутствующие в JSON
> поля и `null` всё равно получают значение типа по умолчанию (`''` для `String`). Init-скрипты выполняются только
> на пустом томе, поэтому при включении профиля `scale` на существующем томе очередь и MV придётся создать вручную.

#### Ключевые параметры `SETTINGS`:
* `kafka_broker_list`: адрес брокера (хост и порт).
* `kafka_topic_list`: имя одного или нескольких топиков через запятую.
* `kafka_group_name`: идентификатор группы консьюмеров (Consumer Group). Брокер фиксирует коммиты смещений (offsets) для этой группы.
* `kafka_format`: формат парсинга сообщений (`JSONEachRow`, `Protobuf`, `Avro`, `CSV` и др.).
* `input_format_null_as_default = 1`: критически важная настройка. Если в JSON пришло поле со значением `null`, ClickHouse не падает с ошибкой, а подставляет дефолтное значение для типа (пустую строку `''` для `String` или `0` для чисел).
* `kafka_handle_error_mode = 'stream'`: сообщение, которое не удалось разобрать (не JSON, неверный тип поля), не останавливает чтение топика. Вместо исключения и бесконечного повтора одного и того же батча движок отдаёт строку с текстом ошибки в виртуальной колонке `_error` (исходное сообщение — в `_raw_message`), а MV такие строки отбрасывает.

---

### Компонент 2: Постоянная физическая таблица (`ENGINE = MergeTree`)
* **Роль:** Долгосрочное аналитическое хранилище на диске.
* **Физическое хранение:** Колонки сжимаются и сохраняются в бинарные файлы на диске, структурированные по партициям и блокам.
* **Поведение:** Именно сюда направляются все аналитические `SELECT`, агрегации и построение дашбордов.

Базовый вариант (в SynaqCore используется `ReplacingMergeTree` с дедупликацией, см. [раздел 5](#5-дедупликация-событий-как-работает-replacingmergetree)
и [`infra/clickhouse/init/01-tables.sql`](../../infra/clickhouse/init/01-tables.sql)):

```sql
CREATE TABLE IF NOT EXISTS tracking_events (
    timestamp DateTime64(3, 'UTC'),
    user_id String,
    event_name String,
    experiment_name String DEFAULT '',
    variant String DEFAULT '',
    event_data String
) ENGINE = MergeTree()
PARTITION BY toYYYYMM(timestamp)
ORDER BY (event_name, user_id, timestamp);
```

---

### Компонент 3: Материализованное представление (`MATERIALIZED VIEW`)
* **Роль:** Мотор всей связки, реактивный потоковый пайплайн трансформации.
* **Поведение в ClickHouse:**
  - В отличие от классических реляционных СУБД (PostgreSQL, Oracle), где Materialized View — это снимок данных по расписанию (`REFRESH`), в ClickHouse Materialized View работает как **триггер на операцию вставки (`INSERT`)**.
  - При появлении `Materialized View`, привязанного к Kafka-таблице, ClickHouse автоматически запускает фоновые воркеры-консьюмеры.
  - Как только из Kafka приходит батч сообщений, он проходит через `SELECT` материализованного представления (где данные можно профильтровать, распарсить JSON, обогатить или переименовать) и мгновенно записывается в целевую таблицу через конструкцию `TO target_table`.

```sql
CREATE MATERIALIZED VIEW IF NOT EXISTS tracking_events_mv TO tracking_events AS SELECT
    timestamp,
    user_id,
    event_id,
    event_name,
    experiment_name,
    variant,
    event_data
FROM tracking_events_queue
WHERE length(_error) = 0;
```

Без фильтра по `_error` в `tracking_events` попадали бы пустые строки с `timestamp` 1970 года на каждое битое сообщение.

## 3. Что такое MergeTree и как оно устроено?

Семейство движков **`MergeTree`** — это фундамент и главное ядро ClickHouse, обеспечивающее колоссальную скорость записи и выборки аналитических данных.

### Принцип работы (LSM-подобная архитектура):
1. **Вставка кусками (Parts):** 
   ClickHouse никогда не пишет данные по одной строчке напрямую в файл таблицы. Каждая вставка (батч) записывается на диск как отдельный неизменяемый фрагмент данных (**Data Part**).
2. **Сортировка при записи:**
   Внутри каждого фрагмента (part) данные **уже физически отсортированы** по ключу, указанному в `ORDER BY`.
3. **Фоновое слияние (Background Merge):**
   В фоновом режиме ClickHouse периодически берет несколько мелких фрагментов и объединяет их в один более крупный фрагмент (отсюда и название — **Merge Tree**, дерево слияния). Во время слияния поддерживается порядок сортировки, удаляются помеченные данные и применяются правила специализированных движков.

### Ключевые секции настройки `MergeTree`:

#### `ORDER BY (колонка1, колонка2, ...)` — Первичный ключ сортировки
* **Внимание:** В ClickHouse первичный ключ **НЕ гарантирует уникальность** записей.
* Он определяет **физический порядок строк на диске** и разреженный индекс (sparse index).
* Разреженный индекс создаётся с шагом (по умолчанию каждые 8192 строки — гранула / granule). Благодаря этому ClickHouse быстро пропускает миллионы ненужных строк при фильтрации по полям из `ORDER BY`.
* **Правило:** Первыми в кортеж `ORDER BY` ставят поля с наименьшей мощностью (cardinality), по которым чаще всего идёт фильтрация (например, `event_name`, затем `user_id`, затем `timestamp`).

#### `PARTITION BY выражение` — Секционирование данных
* Физически разделяет данные на изолированные каталоги на диске (например, помесячно: `toYYYYMM(timestamp)`).
* При запросе с фильтром по дате (`WHERE timestamp >= '2026-10-01'`) ClickHouse полностью игнорирует папки других месяцев, не читая их с диска.
* **Правило:** Не дробите партиции слишком мелко (например, по дням или часам при небольшом потоке данных), иначе возникнет ошибка *"Too many parts in all data in table"*. Оптимальный выбор для большинства случаев — помесячное разбиение.

## 4. Почему важно избегать `Nullable` в высоконагруженных схемах?

В ClickHouse колонки по умолчанию **NOT NULL**. Использование `Nullable(Type)` допускается, но имеет существенные технические последствия:

| Аспект | Обычный тип (например, `String`) | `Nullable(String)` |
| :--- | :--- | :--- |
| **Файлы на диске** | 1 файл данных: `column.bin` | 2 файла: `column.bin` + маска `column.null.bin` |
| **Операции ввода-вывода (I/O)** | Минимальные, читается один непрерывный блок | Удваиваются, нужно читать и декодировать маску |
| **Векторизация (SIMD / CPU)** | Процессор обрабатывает массивы данных без ветвлений | Проверки `is_null` ломают процессорный конвейер инструкций |
| **Скорость `GROUP BY`** | Максимальная | Замедление в 1.5–3 раза |

### Рекомендация:
Если отсутствие значения логически эквивалентно пустоте (например, отсутствие эксперимента или варианта), используйте:
- `String DEFAULT ''` вместо `Nullable(String)`
- `0` вместо `Nullable(UInt32)`

В связке с Kafka всегда включайте настройку `input_format_null_as_default = 1`, чтобы сырые JSON-значения `null` автоматически приводились к дефолтным значениям без падения консьюмера.

## 5. Дедупликация событий: как работает `ReplacingMergeTree`

При доставке сообщений через сеть или Kafka действует гарантия **At-Least-Once** (минимум один раз). Повторные отправки запросов браузером или сбои сети неизбежно приводят к дубликатам.

Для защиты от дублирования в SynaqCore используется движок **`ReplacingMergeTree(timestamp)`**:

```sql
CREATE TABLE IF NOT EXISTS tracking_events (
    timestamp DateTime64(3, 'UTC'),
    user_id String,
    event_id String DEFAULT '',
    event_name String,
    experiment_name String DEFAULT '',
    variant String DEFAULT '',
    event_data String
) ENGINE = ReplacingMergeTree(timestamp)
PARTITION BY toYYYYMM(timestamp)
ORDER BY (event_name, user_id, event_id, toDate(timestamp));
```

### Как ClickHouse понимает, что строки — это дубликаты?
ClickHouse ищет дубликаты **НЕ по таймстемпу**, а строго по совпадению **всех полей из кортежа `ORDER BY`**:
1. Одинаковое `event_name` (например, `'purchase'`)
2. Одинаковый `user_id` (например, `'usr_123'`)
3. Одинаковый уникальный `event_id` (например, `'evt_abc789'`)
4. Одинаковая дата `toDate(timestamp)`

### Какая строка удаляется, а какая остаётся?
В скобках `ReplacingMergeTree(timestamp)` указана колонка **версии**:
* Если пришли 2 строки с одинаковым `event_id`:
  - Строка 1: `timestamp = 14:00:01.100` (старая версия)
  - Строка 2: `timestamp = 14:00:01.250` (повтор)
* ClickHouse сравнивает версии: `14:00:01.250 > 14:00:01.100`.
* Он **удаляет старую строку и сохраняет более свежую**. Если таймстемпы равны, сохраняется любая последняя.

### Когда физически удаляется дубликат? Модификатор `FINAL`
* **При вставке (INSERT):** ClickHouse **не ищет дубликаты сразу**, чтобы не тормозить скорость записи (сотни тысяч строк/сек). Данные сначала пишутся кусками на диск как есть.
* **Фоновое схлопывание (Merge):** Дубликаты удаляются в фоне, когда ClickHouse объединяет мелкие куски (parts) в один крупный.
* **Чтение в реальном времени (`FINAL`):** Если аналитическому запросу нужны гарантированно чистые данные сию секунду (до фонового слияния), в запрос добавляют модификатор `FINAL`:
  ```sql
  SELECT count() FROM tracking_events FINAL WHERE event_name = 'purchase';
  ```
  `FINAL` заставляет ClickHouse схлопнуть дубликаты на лету прямо во время выборки.

### Как это используется в SynaqCore
* `analytics_api` не использует `FINAL` (он дорог на больших таблицах): конверсии и воронки считаются через
  `countDistinct(user_id)`, поэтому несхлопнутые дубликаты на них не влияют. Суммы (например, выручка) до фонового
  слияния могут учитывать дубликат — это известное ограничение.
* Если клиент не передал `event_id`, его генерирует трекер перед записью, поэтому пустых ключей дедупликации в таблице
  нет. JS SDK (`sdk/synaq.js`) генерирует `event_id` ещё на клиенте, так что ретраи из браузера несут один и тот же id.
  Серверным клиентам стоит передавать собственный идемпотентный ключ (например, id заказа): id, сгенерированный трекером,
  у повторной отправки будет другим, и такой дубликат не схлопнется.
* Трекер принимает `timestamp` только в окне [сейчас − 7 дней, сейчас + 5 минут]. Без ограничения одна вставка
  могла задеть больше `max_partitions_per_insert_block` месячных партиций: ClickHouse в режиме прямой записи отклонил бы весь
  `INSERT`, и вместе с «ядовитым» событием пропал бы батч валидных; Kafka engine в профиле `scale` бесконечно
  повторял бы такой батч, и приём вставал бы целиком.
