# ADR 0001. Брокер для приёма событий: Kafka (Redpanda), а не RabbitMQ

- **Статус:** принято
- **Область:** ветка `main` (в планируемом lite-варианте брокера нет, см. [README](../../README.md#main-vs-lite))

## Контекст

Go-трекер (`apps/track_api_go`) принимает поток событий от браузеров и бэкендов и должен доставить их в ClickHouse.
Требования: высокая пропускная способность при пиках, буфер на время недоступности ClickHouse, возможность
перечитать данные (replay) после исправления схемы или ошибки, отсутствие отдельного сервиса-консьюмера,
который нужно деплоить и мониторить.

## Решение

Использовать Kafka API (Redpanda) как журнал событий: трекер публикует JSON в топик `tracking_events`
(ключ — `user_id`) через franz-go, а ClickHouse вычитывает топик сам через `ENGINE = Kafka` и materialized view.
RabbitMQ отклонён: он рассчитан на очереди задач, удаляет сообщение после ACK (нет replay) и не имеет нативной
связки с ClickHouse, сопоставимой с Kafka engine.

## Последствия

- **Плюсы:** нет Python-консьюмера («zero-worker»); Redpanda хранит события, пока ClickHouse недоступен; можно
  сдвинуть offset группы `clickhouse_tracking_cg` и перечитать данные; батчинг и сжатие на стороне продюсера.
- **Минусы:** ещё один stateful-компонент (Redpanda) в стеке; доставка at-least-once — нужна дедупликация
  (`ReplacingMergeTree` по `event_id`); Kafka engine чувствителен к «ядовитым» сообщениям — поэтому
  `kafka_handle_error_mode = 'stream'`, фильтр `_error` в MV и окно допустимого `timestamp` в трекере.
- Для маленьких инсталляций брокер избыточен — отсюда lite-вариант с прямой записью в ClickHouse
  (`EVENT_SINK=clickhouse`) и честным компромиссом: без durable-буфера.

## Приложение: разбор

### 1. Как работает асинхронная публикация в Kafka

Когда сервис `track_api_go` публикует событие, оно проходит через такой конвейер:

```
[HTTP Handler (HandleTrack)]
       │
       ▼ (1) Постановка в ограниченную очередь продюсера в памяти
[Буфер franz-go в RAM] ────► HTTP-клиент сразу получает 200 OK
       │                     (если очередь заполнена — 503 + Retry-After: 1)
       ▼ (2) Фоновый сборщик (linger 5 мс) объединяет события в сжатый батч (zstd)
[Батч сообщений]
       │
       ▼ (3) Один запрос к брокеру
[Брокер Kafka / Redpanda] ───► Запись в конец журнала (append-only log)
       │
       ▼ (4) Подтверждение (ACK)
[Callback доставки: ошибки логируются не чаще раза в секунду]
```

franz-go передаёт в callback структуру `*kgo.Record` вместе с ошибкой. Ошибка говорит только о характере проблемы
(например, `timeout`), а запись содержит контекст: `r.Key` (ключ партиционирования, `user_id`), `r.Value` (исходный
JSON, который можно переотправить) и `r.Topic` / `r.Partition` / `r.Offset`.

### 2. Kafka против RabbitMQ: ключевые различия

| Критерий | RabbitMQ | Apache Kafka / Redpanda |
| :--- | :--- | :--- |
| **Архитектурная модель** | Очередь сообщений (smart broker, dumb consumer) | Распределённый журнал (dumb broker, smart consumer) |
| **Судьба сообщения** | Удаляется после подтверждения (ACK) | Хранится заданное время независимо от чтения |
| **Повторное чтение (replay)** | Невозможно: прочитанное сообщение исчезает | Возможно: консьюмер сдвигает `offset` назад |
| **Модель получения** | Push: брокер сам отправляет сообщения клиентам | Pull: консьюмеры запрашивают батчи по готовности |
| **Маршрутизация** | Гибкая (exchanges: topic, fanout, direct, headers) | Простая: топик и партиция по ключу |
| **Пропускная способность** | Десятки тысяч сообщений/с | Сотни тысяч и больше за счёт батчинга, сжатия и последовательного I/O |
| **Подходит для** | Фоновых задач: email, генерация PDF, джобы | Потоковой аналитики, логов, трекинга, интеграции с ClickHouse |

### 3. Схема интеграции ClickHouse + Kafka

ClickHouse забирает данные из топика сам, силами трёх компонентов:

1. **`ENGINE = Kafka` (буфер чтения):** виртуальная таблица `tracking_events_queue`, фоново вычитывающая топик. На диске ничего не хранит.
2. **`MATERIALIZED VIEW` (триггер на INSERT):** `tracking_events_mv` прогоняет каждый микробатч через `SELECT` и пишет в постоянную таблицу.
3. **`ReplacingMergeTree` (постоянное хранилище):** `tracking_events`, партиционирование `PARTITION BY toYYYYMM(timestamp)`.
