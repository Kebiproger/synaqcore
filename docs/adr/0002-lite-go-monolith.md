# ADR 0002. Lite: Go-монолит synaq на одном VPS 4 ГБ

- **Статус:** принято (ветка `lite`). Заменяет схему из Python-версии (тег `v1-python`, история `main`);
  [ADR 0001](0001-kafka-vs-rabbitmq.md) остаётся в силе для будущего профиля `scale`.
- **Дата:** 2026-10
- **Обновление:** пункт 3 («Прямая запись событий в ClickHouse») заменён [ADR 0003](0003-postgres-default-event-store.md): по умолчанию события пишутся в PostgreSQL, ClickHouse — профиль `scale`. Остальное остаётся в силе; цифры бюджета памяти (4 ГБ, ~3.4 ГБ) относятся к варианту с ClickHouse.

## Контекст

Python-версия SynaqCore (тег `v1-python`) — это `experiment_api` (FastAPI + Redis + Postgres), Go-трекер
`track_api` → Redpanda → ClickHouse Kafka engine, `analytics_api` и Zitadel на общем Postgres. Она показывает
распределённую архитектуру, но для целевого пользователя (стартап, который разворачивает платформу у себя)
избыточна:

- восемь с лишним долгоживущих контейнеров, из них три stateful-хранилища (Postgres, Redis, Redpanda), которым
  нужны память, бэкапы и мониторинг;
- на 4 ГБ RAM стек не помещался с запасом: Redpanda и Redis вместе с ClickHouse и Zitadel съедали бюджет;
- конфиг эксперимента читался из Redis с circuit breaker и fallback на Postgres — две точки отказа на горячем
  пути, хотя набор активных экспериментов крошечный (единицы–сотни строк);
- общий Postgres у бизнес-данных и Zitadel: миграции и нагрузка IdP влияли на БД экспериментов.

Цель lite: 1 VPS, 2 vCPU / 4 ГБ (≈ €5 в месяц), ~1–2 тыс. событий/с, установка одной командой.

## Решение

1. **Один Go-сервис `synaq`** (`apps/synaq`) вместо `experiment_api` и `track_api`: публичная выдача вариантов
   (`/api/v1/variants/...`), admin API экспериментов (`/api/v1/experiments/...`, JWT Zitadel) и трекер
   (`/api/v1/tracker/events`). HTTP-контракт (пути, JSON, коды, тексты `detail`) совпадает с Python-версией;
   его закрепляет smoke-набор `tests/contract` (`make smoke`).
2. **Конфиги экспериментов в памяти процесса.** Неизменяемый снимок, который атомарно заменяется
   (`internal/configcache`). Горячий путь — один `atomic.Load`, без БД и без блокировок. Снимок обновляется:
   после собственной записи admin API (read-your-writes), по Postgres `LISTEN experiments_changed`
   (триггер из миграции `00002_experiments_notify.sql`, дебаунс 50 мс), полным перечитыванием раз в 30 с
   (страховка от потерянных уведомлений) и после переподключения слушателя. При ошибке чтения раздаётся
   предыдущий снимок. Готовность `/readyz` = первый снимок загружен; на ней завязаны healthcheck и старт gateway.
3. **Прямая запись событий в ClickHouse** без брокера (`internal/sink/clickhouse`): ограниченный буфер
   (`CH_BUFFER_SIZE` = 10 000 событий, `CH_MAX_BUFFERED_BYTES` = 64 МиБ), батчи
   `INSERT INTO tracking_events FORMAT JSONEachRow` (`CH_BATCH_SIZE` = 1000 или раз в `CH_FLUSH_INTERVAL` = 1 с,
   `async_insert=1`, `wait_for_async_insert=1`), до 5 попыток с экспоненциальной паузой, после чего батч
   отбрасывается с записью в лог. Буфер полон → `503` + `Retry-After: 1`, запрос никогда не блокируется.
   Проверка ClickHouse при старте best-effort: при недоступности synaq пишет предупреждение и стартует —
   выдача вариантов и admin API от ClickHouse не зависят, состояние приёмника видно в `/health/track`. В ClickHouse только `01-tables.sql`, Kafka-очереди и MV нет.
4. **Отдельный Postgres для Zitadel** (`postgres-zitadel`), бизнес-данные — в `postgres-app`. Учётка
   суперпользователя нужна только одноразовому `zitadel-dbinit`.
5. **Строгие типы в API, `422` в формате FastAPI.** Валидация тел (`internal/api/validate`) повторяет правила
   pydantic-схем Python-версии и формат ошибок `{"detail":[{"type","loc","msg"}]}`, но без lax-приведения:
   вес `"5"`, `5.0` или `true` и `is_active: "yes"` — это `422`, а не молча приведённое значение.
6. **Python `experiment_api` выведен из эксплуатации.** Код удалён из ветки, доступен по тегу `v1-python`.
   Паритет распределения закреплён golden-векторами `apps/synaq/internal/allocation/testdata/golden.json`,
   посчитанными Python-сервером; по ним же проверяются `sdk/python` и `sdk/go`. `analytics_api` остаётся на Python.
7. **Бюджет памяти** задан `mem_limit` каждого контейнера: ~3.4 ГБ на долгоживущие сервисы, остаток — ОС и
   page cache. Go-процессы получают `GOMEMLIMIT` ниже `mem_limit`.

## Последствия

**Плюсы**

- Меньше движущихся частей: нет Redis и Redpanda, один бинарь вместо двух сервисов, нет circuit breaker.
- Выдача варианта не зависит от доступности БД после старта: Postgres можно перезапустить, варианты продолжат
  раздаваться из последнего снимка. Недоступность ClickHouse (в том числе при старте) затрагивает только приём
  событий: выдача вариантов и admin API продолжают работать.
- Стек укладывается в 4 ГБ, CI проверяет контракт HTTP-API на реальном стенде (Postgres + ClickHouse + JWKS).

**Минусы и компромиссы**

- **Нет долговременного буфера событий.** `200` означает «принято в буфер», а не «записано». Батч, который не
  записался за 5 попыток (паузы 0.2 → 0.4 → 0.8 → 1.6 с; в худшем случае батч занимает ~3 с, если соединение отклоняется, и до
  ~53 с, если ClickHouse завис (5 × таймаут 10 с + паузы)), отбрасывается с записью в лог; поэтому при недоступности ClickHouse
  дольше нескольких секунд часть событий теряется, буфер заполняется, и клиенты получают `503` + `Retry-After`
  (повтор — с тем же `event_id`). При падении процесса содержимое буфера теряется (при штатной остановке
  synaq дописывает буфер до 5 с). Для A/B-аналитики допустимо, для биллинга — нет.
- **Дедупликация только в ClickHouse** (`ReplacingMergeTree` по `event_id`, схлопывание при фоновых слияниях).
  Если клиент не передал `event_id`, его генерирует трекер — тогда повтор того же события не схлопнется.
- **Один инстанс.** Горизонтальное масштабирование возможно (каждый инстанс держит свой снимок и слушает
  `NOTIFY`), но в lite не настраивается; рассинхронизация между инстансами ограничена 30 с.
- Admin API и публичная выдача делят один процесс: тяжёлые запросы админки теоретически могут влиять на
  latency выдачи. Аналитика при этом по-прежнему вынесена в отдельный сервис (bulkhead).

**Дальше**

- Профиль `scale` в той же кодовой базе: возвращает Kafka/Redpanda как долговременный буфер (Go-продюсер за
  интерфейсом `sink.Producer`, ClickHouse Kafka engine + MV по [ADR 0001](0001-kafka-vs-rabbitmq.md)) и реплики synaq.
- Дисковый spool для буфера трекера, `/metrics` + профиль Grafana, Caddy с auto-TLS, бэкап и восстановление.
